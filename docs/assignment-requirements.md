## 2. 무엇을 만드는 과제인가

외부 클라우드에 있는 Master Node 1개와 조원들의 로컬 PC에서 실행되는 Worker Node 4개가 TCP 소켓으로 통신하는 분산 Key-Value Store 시뮬레이터를 구현한다.

Master는 5,000개의 Key-Value 작업을 생성하고 Worker들의 Queue 상태를 확인하면서 작업을 분배한다. Worker는 받은 작업을 처리하고, 처리 성공 또는 실패 결과를 Master에 알린다. 특정 Worker의 부하가 커지면 Worker끼리 직접 작업을 이전하고, 작업이 실패하면 Master가 다른 Worker에 재할당한다. 모든 사건은 하나의 전역 논리 시계인 System Clock을 기준으로 로그에 기록한다.

구현에서 확인되어야 하는 핵심 동작은 다음과 같다.

1. Master와 Worker 4개의 TCP 연결
2. 5,000개 Key-Value 생성
3. Worker Queue 상태 기반의 동적 작업 분배
4. Worker별 작업 처리와 80% 성공·20% 실패 시뮬레이션
5. 실패 작업의 Priority Queue 등록과 다른 Worker 재할당
6. Worker 간 P2P 작업 이전을 통한 부하 분산
7. 전역 System Clock 기반 시간 계산과 이벤트 로그
8. 작업 완료 후 통계 출력과 정상 종료

## 3. 필수 시스템 구성

### 3.1 노드 구성

| 구성요소 | 수량 | 실행 위치 | 역할 |
| --- | ---: | --- | --- |
| Master Node | 1 | AWS·GCP 등 외부 클라우드 서버 | 데이터 생성, 작업 분배, 장애 감지·재할당, 전역 시계 및 통계 관리 |
| Worker Node | 4 | 조원들의 로컬 PC | Queue 관리, 작업 처리, 결과 보고, P2P 부하 분산 |

### 3.2 통신과 동시성

- Master와 Worker는 TCP 소켓으로 통신해야 한다.
- Worker와 Worker 사이의 P2P 통신도 TCP 소켓으로 구현해야 한다.
- 모든 Worker Node는 각각 독립적인 Thread로 동작해야 한다.
- 동시성 구현을 멀티프로세싱으로 대체하지 않는다.
- 공유되는 Queue, System Clock, 통계, 로그 등에 동시 접근할 때는 Lock 등 적절한 동기화 수단을 사용한다.
- Worker는 실행 시 Master의 공인 IP와 포트로 접속한다.
- Master IP와 포트는 프로그램 실행 시 명령행 인자 또는 설정 파일로 지정할 수 있어야 한다.

### 3.3 전체 0점이 되는 필수 조건

다음 중 하나라도 충족하지 못하면 과제 전체가 0점 처리된다.

- Master를 AWS·GCP 등 물리적으로 외부에 있는 클라우드 서버에 구성하지 않은 경우
- Master↔Worker 및 Worker↔Worker 통신을 TCP 소켓으로 구현하지 않은 경우
- 모든 Worker를 독립 Thread로 구현하지 않은 경우
- 제출한 소스코드가 컴파일되지 않거나 실행되지 않는 경우
- 제출 ZIP 파일에 오류가 있어 정상적으로 압축 해제할 수 없는 경우

## 4. Key-Value 데이터 요구사항

- Master가 총 **5,000개**의 Key-Value 쌍을 생성한다.
- Key는 중복되지 않는 4자리 16진수 문자열이다.
  - 예: `0000`, `00af`, `a3f7`, `ffff`
- Value는 1~100 사이의 정수다.
- Key-Value 저장소는 Map 계열 자료구조로 구성하여 Key 기준 평균 O(1) 접근을 제공한다.
- 성공적으로 처리된 결과는 최종 Key-Value 저장소에 반영한다.

## 5. 전역 System Clock

### 5.1 의미

- System Clock은 OS의 실제 시각이 아니라 시뮬레이션 전체에서 공유하는 **가상의 누적 시간**이다.
- 별도의 전역 Clock 객체를 두고 모든 노드와 이벤트가 같은 논리 시각을 사용해야 한다.
- System Clock은 0초에서 시작한다.
- 모든 로그에는 이벤트가 발생한 System Clock 값이 포함되어야 한다.
- 실제 프로그램은 `sleep()`으로 논리 시간만큼 기다리지 않고 빠르게 실행한다.

### 5.2 시간 반영 규칙

- 작업 처리에는 1~3초의 무작위 가상 처리시간을 반영한다.
- 노드 간 통신에는 1초의 가상 통신 지연을 반영한다.
- 작업 처리와 통신에 따라 Clock을 갱신하며, 전체 수행시간도 System Clock을 기준으로 계산한다.
- 여러 Thread가 Clock을 동시에 갱신할 수 있으므로 원자적 갱신 또는 Lock이 필요하다.

## 6. Worker Ready Queue

- 각 Worker의 Ready Queue 최대 크기는 10이다.
- Worker는 Queue에 들어온 작업을 순서대로 처리한다.
- Queue에 10개의 작업이 있는 상태에서 추가 요청이 들어오면 해당 요청은 즉시 FAIL 처리한다.
- Queue가 가득 찬 Worker에는 Master가 작업 분배를 일시 중단해야 한다.
- Queue가 70%를 초과한 상태에서는 작업이 들어오거나 나갈 때마다 WARN 이벤트를 기록한다.
- Queue에 작업이 들어오거나 나갈 때마다 관련 상태를 갱신하고 로그로 남긴다.

## 7. 동적 작업 분배

Master는 각 Worker의 현재 Queue 사용량과 처리 상태를 지속적으로 확인하고 작업을 동적으로 분배한다.

필수 동작:

1. 현재 Queue에 남은 공간이 가장 많은 Worker를 우선 선택한다.
2. Queue가 최대 크기 10에 도달한 Worker에는 분배를 중단한다.
3. 다른 Worker를 선택하여 작업 분배를 계속한다.
4. 총 5,000개 작업이 모두 분배·처리될 때까지 반복한다.
5. 작업 전송에는 1초의 가상 통신 지연을 반영한다.

동적 작업 분배 알고리즘의 구체적인 방식에는 제한이 없지만 다음 내용을 `Readme.txt`에 반드시 명시해야 한다.

- 선택 기준과 동작 순서
- 시간·공간 복잡도
- 장점과 단점

## 8. Worker 작업 처리

- Worker는 작업 하나당 1~3초의 무작위 가상 처리시간을 적용한다.
- 각 작업은 다음 확률을 가진다.
  - 성공: 80%
  - 실패: 20%
- 성공하면 Worker가 Master에 SUCCESS 결과를 전송하고 Master가 Key-Value 저장소를 갱신한다.
- 실패하면 Worker가 Master에 FAIL 결과와 작업 식별자를 전송한다.
- 성공·실패 확률은 실제 실행 때마다 시뮬레이션되어야 한다.

## 9. 장애 처리와 재할당

작업 실패 시 다음 순서로 장애를 복구한다.

1. Worker가 작업 실패를 감지한다.
2. Worker가 Master에 FAIL 메시지와 실패 작업 ID를 전송한다.
3. Master가 실패 작업을 Priority Queue에 등록한다.
4. Master가 현재 Queue 여유 공간이 가장 큰 다른 Worker를 선택한다.
5. 실패 작업을 일반 작업보다 우선하여 재할당한다.
6. 재할당된 작업에도 동일한 80% 성공·20% 실패 규칙을 적용한다.
7. 다시 실패하면 Priority Queue에 재등록하고 성공할 때까지 반복한다.
8. 성공하면 최종 Key-Value 저장소를 갱신한다.

장애 처리 알고리즘과 재시도 정책은 `Readme.txt`에 설명해야 한다.

## 10. Worker 간 P2P 부하 분산

### 10.1 동작 조건

각 Worker는 자신의 예상 대기시간을 주기적으로 계산한다.

```text
예상 대기시간 = Queue에 남은 작업 수 × 평균 처리시간 2초
```

- 예상 대기시간이 15초를 초과하면 P2P 부하 분산을 시작한다.
- 각 Worker는 예상 대기시간을 1~3초 사이의 랜덤 주기로 반복 점검한다.
- 과부하 Worker는 인접 Worker들의 Queue 상태를 TCP 소켓으로 조회한다.
- 여유 있는 Worker를 선택하여 작업 이전을 요청한다.
- P2P 알고리즘은 자유롭게 설계할 수 있다. 이 저장소의 기본 설계에서는 이전 작업 수를 1~3개 사이에서 무작위로 결정한다.

### 10.2 안전한 작업 이전

1. 송신 Worker가 수신 Worker의 Queue 여유를 확인한다.
2. 송신 Worker가 TCP 소켓으로 작업을 전송한다.
3. 수신 Worker가 작업을 자신의 Queue에 추가한다.
4. 수신 Worker가 ACK를 전송한다.
5. 송신 Worker는 ACK를 받은 뒤에만 자기 Queue에서 해당 작업을 제거한다.
6. 이전 내역과 Queue 변화는 양쪽 Worker 로그에 기록한다.

P2P 부하 분산 알고리즘의 방식에는 제한이 없지만 다음 내용을 `Readme.txt`에 반드시 명시해야 한다.

- 작업 이전 개수 결정 방식
- ACK와 실패 처리 방식
- 시간·공간 복잡도
- 장점과 단점

## 11. 전체 시뮬레이션 흐름

### Step 1. 초기화

- Master가 먼저 실행된다.
- System Clock을 0초로 초기화한다.
- Master가 5,000개의 Key-Value 작업을 생성한다.
- Worker 4개가 순차적으로 Master에 접속한다.
- 각 Worker가 Ready Queue를 초기화한다.
- Worker 4개 연결이 완료되면 작업 분배를 시작한다.

### Step 2. 동적 작업 분배

- Master가 Worker별 Queue 상태를 확인한다.
- Queue 여유 공간이 가장 많은 Worker에 작업을 우선 배정한다.
- Queue가 가득 찬 Worker에는 배정을 일시 중단한다.
- 5,000개 작업 전체에 대해 반복한다.

### Step 3. 작업 처리와 결과 수집

- Worker가 Queue의 작업을 처리한다.
- 1~3초의 가상 처리시간과 80:20 성공·실패 규칙을 적용한다.
- 결과를 Master에 보고한다.
- 실패 작업은 Priority Queue를 거쳐 재할당한다.

### Step 4. P2P 부하 분산

- Worker가 예상 대기시간을 계산한다.
- 15초 초과 시 여유 있는 Worker에 1~3개 작업을 이전한다.
- Worker 간 작업 이전과 ACK를 로그에 기록한다.

### Step 5. 종료와 통계

- 모든 5,000개 작업이 성공적으로 처리되면 Master가 종료 신호를 전송한다.
- 각 Worker가 최종 통계를 출력하고 로그에 기록한다.
- Master가 전체 저장소 결과와 노드별 통계를 기록한다.
- 모든 소켓 연결과 Thread를 정상적으로 종료한다.

## 12. 성능 평가 지표

과제 설명 자료에는 필수 측정 항목이 6개 나열되어 있으므로 다음 항목을 모두 구현한다.

| 지표 | 단위 | 설명 |
| --- | --- | --- |
| Worker별 작업 처리량 | 건 | 각 Worker가 성공적으로 처리한 Key-Value 작업 수 |
| Worker별 성공·실패 횟수 | 건 | Worker별 성공 횟수와 20% 실패 시뮬레이션 횟수 |
| 작업 평균 대기시간 | sec | Queue 진입부터 처리 시작까지의 평균 논리 시간 |
| P2P 부하 분산 이벤트 횟수 | 회 | Worker 간 작업 이전 발생 횟수 |
| 장애 재할당 횟수 | 건 | 실패로 인해 다른 Worker에 재할당된 작업 수 |
| 전체 수행시간 | sec | System Clock 기준 전체 시나리오 완료 시간 |

다음과 같은 추가 통계도 로그에 포함하는 것이 권장된다.

- Queue overflow reject 횟수
- 재시도 작업 수
- Worker가 보낸 작업과 받은 작업 수
- 최종 저장된 Key-Value 쌍 수

## 13. 로그 요구사항

### 13.1 공통 형식

모든 노드는 다음 공통 형식으로 이벤트를 기록한다.

```text
[clock] NODE | EVENT | STATUS | message
```

### 13.2 STATUS

STATUS는 다음 중 하나만 사용한다.

- `INFO`
- `SUCCESS`
- `FAIL`
- `WARN`

### 13.3 EVENT

EVENT 이름은 자유롭게 정의할 수 있다. 예시는 다음과 같다.
